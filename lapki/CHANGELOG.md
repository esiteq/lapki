### Email-шаблони — перехід на WP_List_Table + нова конвенція для нових таблиць адмінки

- Сторінка `Lapki → Email-шаблони` переписана з AJAX/JS-рендеру (клієнтський `loadEmailTemplates()`/`renderEmailTemplatesTable()`) на нативний `WP_List_Table`: нова `Lapki_Email_Templates_List_Table` (`class-lapki-admin.php`) — серверний рендер напряму з `Lapki_Email_Template::get_all()`, без окремого REST GET для списку (усуває клас проблем із застарілим кешем JS, що вже проявився в попередній сесії).
- Колонка "Призначення" — нативний WordPress row-actions (`$this->row_actions()`): посилання "Редагувати" з'являється при наведенні на рядок стандартним адмін-CSS ядра (без власного hover-CSS). Дані для модалки (subject/body/placeholders) — прямо в `data-*` атрибутах посилання, JS відкриває модалку без додаткового запиту.
- `js/lapki-admin.js`: `initEmailTemplatesList()` спрощено (лише обробники модалки + делегування кліку на `.lapki-email-edit`), прибрано `loadEmailTemplates`/`renderEmailTemplatesTable`/`emailTemplatesCache` — більше не потрібні. `saveEmailTemplate()` після успіху робить `window.location.reload()` замість клієнтського ре-рендеру.
- REST `PUT /email-templates/{id}` лишився без змін (усе ще через нього зберігається).
- **Уточнення за проханням користувача:** `Lapki_Email_Templates_List_Table::prepare_items()` не звертається до моделі напряму — дані отримує через `rest_do_request()` (внутрішня диспетчеризація того самого REST-контролера `GET /email-templates`, без реального HTTP-запиту). Так пряме звернення до БД/моделі лишається виключно всередині REST-контролера — єдина точка доступу до даних і для серверного рендеру, і для клієнтського JS.
- **Нова конвенція, зафіксована в CLAUDE.md:** усі нові таблиці в адмінці Lapki — тільки через `WP_List_Table`, `Lapki_Email_Templates_List_Table` — еталонна реалізація; читання даних — через `rest_do_request()` до власного REST-контролера, не напряму до моделі. Існуючі AJAX-таблиці (Тварини/Організації/Атрибути) заднім числом не переписувались — конвенція стосується нових таблиць.
- `LAPKI_VERSION` → `2.0.44`.
- Перевірено через `wp eval`: рендер сторінки містить `row-actions`, посилання "Редагувати", назву засіяного шаблону, немає спінера в розмітці (серверний рендер); `data-body` коректно екранований (`esc_attr`, підтверджено на реальному апострофі в тексті шаблону). `php -l`/`node --check` — без помилок.

- Нова таблиця `wp_lapki_email` (`id, slug, name, subject, body, placeholders, created_at, updated_at`), `Lapki_Migrations::DB_VERSION` → `2.18.0`. Засіяно один шаблон — "Заявка на прилаштування" (`slug=application_owner_notification`), текст перенесено з існуючого хардкоду в `send_application_emails()`, параметризовано мітками `{animal_name}`, `{applicant_name}`, `{applicant_email}`, `{applicant_phone}`, `{applicant_message}`, `{applications_url}`.

- Нові REST-маршрути `GET /email-templates`, `PUT /email-templates/{id}` — доступ лише `manage_options` (окремий permission callback `check_manage_email_templates_permission`, не одна з capability `lapki_manage_*`, бо це загальносайтове налаштування, не прив'язане до конкретної організації).
- `send_application_emails()`: лист власнику тварини (притулку або приватній особі — обидва випадки й далі покриваються `organization.email`, нову логіку вибору отримувача додавати не знадобилось) тепер рендериться з шаблону в БД замість хардкоджених `sprintf()`-рядків, з фолбеком на старий хардкод, якщо шаблон відсутній. Лист-підтвердження заявнику свідомо лишили хардкодженим — поза межами цього завдання.
- Нова сторінка `Lapki → Email-шаблони` (`lapki-email-templates`): таблиця (Призначення / Subject / Дата редагування / Дії) + модалка редагування Subject і тіла листа з підказкою доступних міток. Без додавання/видалення шаблонів — навмисно, за завданням. JS (`initEmailTemplatesList`, `loadEmailTemplates`, `renderEmailTemplatesTable`, `showEmailTemplateModal`, `saveEmailTemplate`) і CSS (`.lapki-email-modal-*`) — за тим самим патерном, що й редактор атрибутів.
- Перевірено на бойовому сайті через `wp eval-file`: `GET`/`PUT` через модель напряму (оновлення subject, читання назад, відкат), `render()` з підстановкою міток, permission callback (анонім → заборонено, адмін → дозволено), валідація (порожні поля → 400, неіснуючий id → 404), і наскрізно — створення тестової заявки на реальну тварину з перехопленням `wp_mail` через фільтр: лист власнику сформувався саме з шаблону БД з коректно підставленими мітками, лист-підтвердження заявнику не змінився; тестову заявку видалено після перевірки. `php -l`/`node --check` — без помилок.
- **Знайдено і виправлено баг:** сторінка "Email-шаблони" показувала нескінченний спінер — `wp_enqueue_script('lapki-admin', ..., LAPKI_VERSION, true)` кешбастить за статичною константою `LAPKI_VERSION`, не за `filemtime()`, тож без її бампу браузер продовжував віддавати стару закешовану `lapki-admin.js` без нових функцій. `LAPKI_VERSION` → `2.0.43`.

### Виправлено — гео-радіус (сесія 52) з одночасно заповненим текстовим містом повертав 0 результатів

Користувач повідомив: ввів "Київ" у поле "Місто" + лишив увімкненим гео-чекбокс (радіус від реального розташування браузера) → "Нічого не знайдено", хоча тварини в Києві є. ### Виправлено — "Покращити за допомогою ШІ" видавало "Помилка з'єднання" (502)

Два незалежні реальні баги, обидва знайдені живим тестуванням з реальним ключем (не тільки код-рев'ю):

1. **Cloudflare підміняв тіло помилки** — `/ai/improve` навмисно повертав HTTP 502/503 для помилок провайдера/відсутнього ключа; Apache-логи (`sudo tail /var/log/apache2/lapki_access.log`) підтвердили, що origin щоразу коректно віддавав валідний JSON (жодного PHP-краху чи таймауту в `lapki_error.log`/`debug.log`) — але Cloudflare за замовчуванням перехоплює 502/503/504 (і 520-527) і підміняє тіло власною HTML-сторінкою помилки ще ДО браузера, навіть якщо origin відповів нормально. Тому `fetch().then(r => r.json())` падав на невалідному HTML, і користувач бачив загальний catch-фолбек "Помилка з'єднання", а не справжнє повідомлення від Gemini. Виправлено: обидва статуси (`ai_not_configured`, `ai_request_failed`) в `class-lapki-rest-api.php::ai_improve_text()` тепер `500` — цей код Cloudflare типово не перехоплює.
2. **Захардкоджені назви моделей Gemini вже зняті з обслуговування** — `gemini-2.5-flash`/`-flash-lite`/`-pro` і `gemini-2.0-flash`/`-flash-lite` (усе, що було в списку сесії 36) повертали 404 "no longer available to new users" при живому виклику з реальним ключем — Google, вочевидь, зняв ці версійні назви з обслуговування для нових ключів улітку 2026. Перевірено живими запитами до `generativelanguage.googleapis.com` з реальним ключем: замінено на `-latest`-аліаси (`gemini-flash-latest` — новий дефолт, `gemini-flash-lite-latest`, `gemini-pro-latest` — реально відповіли 200; `gemini-pro-latest` при цьому впирається в нульовий безкоштовний ліміт, позначено в описі опції). Такі аліаси самі перемикаються на актуальну модель, тому мають рідше вимагати ручного оновлення коду в майбутньому — на відміну від версійних назв.

Справжній корінь — **застарілі підказки ніколи не прибираються з випадаючого списку**.
