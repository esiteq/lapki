## Свідомі обмеження обсягу / відомі пробіли

- **Локалізація не 100%**: покриті тільки нові/найбільш «дороті» рядки (меню, помилки API, налаштування). Повне обгортання адмін-HTML, фронтенд-шаблонів і JS в `__()`/`wp.i18n` — окрема велика задача.
- **Не покрито тестами**: успішне завантаження файлу через `POST /animals/{id}/media` (`upload_animal_media` викликає `move_uploaded_file()`, який завжди повертає `false` поза справжнім HTTP-запитом; перевірено лише межу авторизації endpoint'у, 403 без capability).
- **Не реалізовано**: публічна фронтенд-форма самостійного додавання тварини (`/add-animal/`, посилання в темі поки веде в нікуди — рендерить дефолтний `page.php` теми), сторінка "Про нас"/"Контакти"/"Privacy policy" з футера — не було в explicit todo-скоупі цієї сесії.
- **Node.js `server/`** — свідомо не чіпали (за прямою вказівкою користувача: міграція на Node.js відбудеться тільки після повного тестування і готовності WP-плагіна до продакшену).
- Email надсилається через стандартний `wp_mail()` — залежить від налаштованого SMTP на сервері; не перевірялося з реальною доставкою (лише що виклик відбувається без помилок).

## Швидка перевірка (як я тестував зміни)

- REST API: `wp eval` з `rest_do_request()` для анонімного/адмінського доступу (create/update/delete тварин, організацій, атрибутів, заявок).
- Фронтенд: `curl` по `/animals/`, `/animals/1/`, `/organizations/`, `/organizations/1/` — усі 200, неіснуюча тварина — 404.
- Адмінка: рендер `organizations_page()`/`settings_page()` напряму через `wp eval` (WP-CLI не встановлює `is_admin()`), перевірено на відсутність PHP-помилок.
- `php -l` і `node --check` на всіх змінених PHP/JS файлах.
- `tail` логів Apache після тестів — нових помилок не з'явилось.

### 🔴 Критично — знайдено цією сесією

- [x] **Плагін не закомічено ~2 місяці / ~90+ сесій розробки.** Закрито 2026-09-10: усі накопичені зміни (сесії 31-110) закомічено одним squash-комітом `85871fd` "Sync 90+ sessions of work..." і запушено на `esiteq/lapki` — за прямим підтвердженням користувача (варіант "усе одним комітом"). Перед комітом перевірено відсутність секретів (Gemini API-ключ — у `wp_options`, не хардкод) і виключено сторонній незакомічений плагін `wp-content/plugins/themegrill-demo-importer/`, що лежить у тому самому репозиторії однією директорією вище `lapki/`. Деталі — [[project_lapki_git_backlog]].

- [ ] **Перемикання мови кукою (без мовного префікса в URL) не застосовує переклад над реальним HTTP-запитом — знайдено 2026-09-10, сесія 111, під час перевірки `/help/` в EN.** Відтворюється на БУДЬ-ЯКІЙ сторінці без мовного префікса (перевірено на `/organizations/` і новій `/help/`): `Lapki_I18n::get_lang()`/`determine_locale()` коректно повертають `en_US` (перевірено — `<html lang="en-US">` виставляється правильно), але фактичний текст (навіть давно перекладені рядки на кшталт "Собаки"/"Про нас" у футері) лишається українською. Той самий сценарій **коректно працює** через `wp eval` (пряме виконання PHP: `__('Собаки','lapki')` → `Dogs`) і через мовний префікс в URL (`/en/blog/…` — перевірено окремо, працює). Отже сама мовна логіка й скомпільовані `.mo` справні — розбіжність десь між реальним HTTP-запитом (Apache/PHP-FPM) і `WP_Textdomain_Registry`/just-in-time завантаженням перекладів для JIT-домену `lapki`.
  - Виключено як причину (перевірено): Cloudflare-кеш (`cf-cache-status: DYNAMIC` — наскрізь, не кешується), кеш-плагіни (`wp plugin list` — активний лише сам `lapki`), персистентний object cache (`wp_using_ext_object_cache()` → false, `wp-content/object-cache.php` відсутній), артефакт curl-редиректу (відтворено і без жодного редиректу, напряму через `curl --resolve lapki.help:443:127.0.0.1`).
  - Код WP-ядра (`get_locale()`, `determine_locale()`, `_load_textdomain_just_in_time()`, `WP_Textdomain_Registry::get()`) при уважному прочитанні виглядає коректним і locale-aware — не знайдено очевидного багу в самому механізмі під час рев'ю коду.
  - Впливає потенційно на ВЕСЬ публічний фронтенд без мовного префікса (`/organizations/`, `/animals/`, `/donate/`, `/profile/`, `/help/` тощо) — тобто перемикач UA/EN може не працювати для анонімних відвідувачів на більшості сторінок сайту, лишаючи лише `/en/blog/` і `/en/about/` (з мовним префіксом в URL) дійсно робочими.
  - Наступний крок розслідування: порівняти PHP SAPI/конфігурацію (`php.ini`, opcache-налаштування) між CLI (`wp eval`, де все працює) і PHP-FPM (де не працює) — зокрема `opcache.validate_timestamps`/preloading і будь-які APCu-виклики поза стандартним WP Object Cache API (жодних не знайдено в коді плагіна/теми, але варто перевірити mu-plugins і php.ini-рівневі drop-in'и, яких не перевіряли).
